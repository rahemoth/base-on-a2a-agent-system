# RAG 记忆系统：运作原理

> 这份文档解释 `backend/agents/rag_*.py` 这套记忆系统**整体上是怎么运转的**，以及每个算法**为什么这么做、逻辑是什么**。不贴代码，只讲思路。

***

## 一句话概括

Agent 每次对话的内容，会被**压缩**成若干带摘要的记忆块，存进一个**向量数据库（ChromaDB）**里；下次提问时，系统把问题变成向量，去索引里**找最相关的几条记忆**，再交给大模型作为上下文。同时用 **LLM 抽取中文实体和语义关系三元组**，维护一张**实体关系图**支持多跳推理，并用一个**一致性管理器**避免记忆自相矛盾。向量索引和实体图都持久化到磁盘，进程重启不丢。

***

## 为什么需要这套东西

大模型本身没有长期记忆，每次对话都是"从零开始"。如果直接把所有历史对话塞回上下文，很快就会撑爆 token 上限。所以需要一套机制做到三件事：

1. **压缩**：把长对话变短，但保留关键信息
2. **检索**：提问时只取相关的几条，不是全部
3. **一致**：新信息和旧信息冲突时，知道该更新还是该删除

这就是 RAG（Retrieval-Augmented Generation，检索增强生成）记忆系统做的事。

***

## 三层记忆

| 层   | 存什么           | 怎么查      | 类比                    |
| --- | ------------- | -------- | --------------------- |
| 热记忆 | 最近几轮原始对话      | 直接按顺序取   | 工作台上的便签               |
| 温记忆 | 压缩后的对话摘要 + 向量 | 语义相似度检索  | 档案柜，按内容找              |
| 冷记忆 | 实体和实体之间的关系    | 图遍历、多跳推理 | 人脉网，"A 认识 B，B 在 C 公司" |

热记忆保证近期上下文不丢；温记忆是主力，海量历史按语义找；冷记忆负责"推理型"问题，需要串联多个事实时用。

***

## 整体流程

### 存入记忆

```
对话发生
  ↓
1. 分块：把对话按每 5 轮切成 chunk
  ↓
2. 压缩：相似的 chunk 合并，直到达到压缩目标（比如压到原来的 30%）
  ↓
3. LLM 抽取实体 + 关系（开启时）：
   • 调 agent 自己的 LLM，要求返回 JSON：实体列表 + 主-谓-宾三元组
   • 抽不到（未开启 / 无 LLM client / 调用失败）→ 回退到"同段共现"
  ↓
4. 入 ChromaDB 向量库 + 内存倒排/时间索引：
   • 向量、内容、实体、关系三元组都写进 ChromaDB（持久化）
   • 倒排索引（实体/关键词）和时间索引仍留内存，启动时从 ChromaDB 重建
  ↓
5. 建记忆图：实体做节点，LLM 给的语义关系（"研究"/"合作"/"位于"）做边
  ↓
6. 一致性检查：这条新记忆和已有的某条很像吗？
   像但不矛盾 → 更新合并
   像且矛盾   → 删除旧的
   不像       → 当作新事实存下
```

### 查询记忆

```
用户提问
  ↓
1. 把问题转成向量（embedding）
  ↓
2. 先查缓存：同样的问题问过吗？问过直接返回
  ↓
3. 没缓存就做混合检索：
   • 先按实体/时间/关键词粗筛出一批候选
   • 再在这批候选里做向量相似度搜索
   • 最后按"相似度 × 新鲜度"重排
  ↓
4. 可选：开启图推理时，从相关实体出发做多跳路径搜索，补充关联事实
  ↓
5. 返回 top-k 条记忆，作为大模型的上下文
```

## 各个算法的逻辑

### 1. 向量索引——怎么在几十万个向量里快速找最近的几个

**两种后端，可切换**：

- **HNSW（默认，纯内存）**：不配 ChromaDB 时用它，零依赖、快，但重启丢
- **ChromaDB（持久化）**：agent 配了 `chroma_persist_dir` 就用它，向量落盘到 `data/chroma/`，重启不丢

两者对外接口一样（增删查统计），`HybridRetrievalSystem` 内部根据初始化参数二选一，上层无感。没装 chromadb 包时自动回退 HNSW。

**HNSW 的思路**：借鉴"跳表"的思想，建一个**多层图**。

- 最底层有全部节点，连接密集；往上每层节点数指数级减少，连接稀疏。
- 顶层像"高速公路"，少数节点用长距离边跨大范围；底层像"小路"，密集连接做精确局部搜索。

**搜索时**：从最高层入口出发，每层贪心地往最近的邻居走，一层层往下细化，最后在最底层用更大的候选集做精搜。效果是 `O(log N)` 而不是 `O(N)`。

**插入时**：随机给新节点分一个层级（服从几何分布，越高层概率越低）。从顶层往下，每一层都找它最近的几个节点连边。关键两点：

- **边必须双向**——只连出去不连回来，图就走不通了
- **入口点切换时，下层搜索要从旧入口开始**——新节点在低层还没插入，从它自己出发会找不到任何邻居，变成孤岛

**邻居选择**：每层最多连 M 个最近的。简单直接，不用花哨的启发式（早期实现用一个"20% 容差"规则过度丢弃邻居，导致大量节点变孤岛、图不连通，后来改回朴素取最近 M 个）。

**ChromaDB 后端**：不用自己建图，直接把向量交给 ChromaDB（用余弦距离的 HNSW 索引），它内部做 ANN 搜索。我们的 embedding 由 `EmbeddingService` 预生成再传进去，不让 ChromaDB 自己调 embedding 函数——保证维度和项目其他路径一致。每个文档的 metadata 里除了 chunk 信息，还塞了 `entities` 和 `relations` 的 JSON，用于重启时重建记忆图。

### 2. 对话压缩——怎么把长对话变短还不丢关键信息

**思路**：层次聚类合并。

1. **分块**：每 5 轮切一段
2. **找相似的对**：用 LSH（局部敏感哈希）快速筛出可能相似的 chunk 对，避免两两比较的 `O(N²)`
3. **打分**：合并优先级 = 语义相似度 × 信息密度。信息密度综合考虑实体密度、用户消息占比、时间新鲜度
4. **合并**：把最该合并的两段合成一段，embedding 取加权平均，实体取并集
5. **重复**：一直合并到总轮数压到目标比例为止

信息密度低、又相似的对话段，优先被合并掉；信息密度高（提到很多实体、用户主动提问）的段保留更多。

可选升级版用小 LLM 给每个 chunk 生成文字摘要，比纯向量合并保留更多可读信息。

### 3. 混合检索——怎么又快又准地找到相关记忆

单靠向量相似度不够：有时候你想"上周关于 Alice 的对话"，这就需要实体过滤 + 时间过滤。所以建三个索引一起用：

- **倒排索引**：实体 → 出现过它的文档列表；关键词 → 文档列表
- **时间索引**：按时间排序的 B+ 树，支持范围查询
- **向量索引**：上面的 HNSW

**检索分三阶段**：

1. **粗筛**：用实体/关键词/时间过滤器交集，圈出一批候选文档
2. **精搜**：候选少就暴力算余弦相似度；候选多就走 HNSW
3. **重排**：`最终分 = 0.7 × 相似度 + 0.3 × 新鲜度`，新鲜度按 1 周衰减。兼顾"语义相关"和"越新越重要"

### 4. 记忆图与多跳推理——怎么回答"A 通过谁认识 B"这类问题

**记忆图**：节点是实体（人、概念、地点），边是关系。

边从哪来？**优先用 LLM 抽取的语义关系三元组**——同一段对话送给 agent 自己的 LLM，要求返回 JSON：实体列表（带类型）+ 主-谓-宾三元组。比如"张三在北京大学研究人工智能，他和李四合作"会抽出：

- 实体：张三(person)、北京大学(organization)、人工智能(concept)、李四(person)
- 关系：张三--研究-->人工智能、张三--位于-->北京大学、张三--合作-->李四

这些边的 `relation_type` 就是 LLM 给的中文动词（"研究"/"合作"/"位于"），比共现有意义得多，多跳推理能真正回答"张三和李四什么关系"。

**回退机制**：LLM 抽取没开、没 client（如 Gemini agent）、调用失败、或返回空时，退回**同段共现**——同一段对话里被一起提到的两个实体建一条 `co_occurs` 边。共现是合理近似但无语义，至少保证图不会空。

**持久化**：实体和关系都序列化成 JSON 存进 ChromaDB 文档的 metadata。重启时从 metadata 重建图，多跳推理立即可用，不用等新对话进来。

**多跳推理用 Beam Search**：

- 从起始实体出发，维护一个宽度为 b 的"beams"（当前最看好的 b 条路径）
- 每一步，把每条路径沿边扩展一格，用启发式给新路径打分
- 启发式 = 语义对齐（路径终点实体和问题的向量有多近）+ 时间新鲜度 + 跳数惩罚（鼓励短路径但允许长路径）
- 每步只保留 top-b，最后返回最长的几条（多跳推理的目的就是到达远端实体，所以优先长路径）

这样能回答"通过哪些中间事实，从 A 关联到 B"这类需要串联的问题。

### 5. 一致性管理——怎么避免记忆自相矛盾

新记忆进来时，先和已有的每条算相似度：

- **很像（相似度 ≥ 0.85）**：大概率是同件事
  - 新内容含否定词（"不再"、"没有"、"其实"）且提到同样的实体 → **判定为矛盾，删掉旧的**
  - 否则 → **更新**：把新旧两版按句子去重合并，保留最早时间戳、取最高置信度
- **有点像（0.6 \~ 0.85）**：看用词重叠率，重叠多就更新，重叠少就当新事实
- **不像（< 0.6）**：直接当新事实存下

这样记忆库不会因为同一个事实反复陈述而膨胀，也不会"A 在 X 公司"和"A 不在 X 公司"同时存在。

**向量时钟**用来跟踪因果关系——谁先谁后、是否并发。关键是要遍历**两个时钟所有出现过的副本**，不能只看自己的，否则会把"互相独立的事件"误判成有先后。

### 6. 性能优化

- **LRU 缓存**：高频重复的查询直接返回缓存结果，`O(1)`。新记忆写入时清缓存，避免返回过期结果
- **乘积量化（PQ）**：把向量切成若干子空间，每个子空间用聚类中心编号代替原向量，从 32-bit 压到 8-bit，大幅省内存（已实现，检索路径还没接入）
- **查询优化器**：记录哪些查询最频繁，可以预热缓存
- **性能监控**：记录每个操作的耗时分布（mean/p50/p95/p99）

## 几个关键的工程细节

这些是实际跑通才发现的非显然点：

1. **缓存键要用完整向量的 hash**，不能只用前几维——不同向量前缀相同会撞车，返回错误结果
2. **缓存命中标记要在查缓存时就记录**，而不是查完写入后再判断——否则永远是"命中"
3. **写入新数据后要清缓存**——否则同问题永远返回旧结果，新记忆查不到
4. **时间戳要统一时区**——数据库存的带时区，对话块生成的不带时区，比较时会崩。统一规则：没带时区的当作 UTC
5. **numpy 数组不能直接 `if` 判断真假**——`if embeddings:` 会报歧义错误，要用 `is not None`
6. **beam search 要保留所有发现过的路径**——每轮只留新扩展的，路径一旦到终点没法再扩展，就全丢了
7. **ChromaDB metadata 只能存基本类型**（str/int/float/bool），嵌套结构（实体列表、关系三元组）要先 JSON 序列化成字符串，读出来再反序列化
8. **实体图持久化要在写入向量时就带上关系**——不能先写向量再回补 metadata，ChromaDB 的 metadata 在 `add` 时一次写定；所以抽取必须放在写入之前
9. **LLM 抽取的 model 要用 agent 自己的 config.model**，不能用固定的 `gpt-4o-mini`——不同 provider 支持的模型名不同，mimo 不认 gpt-4o-mini，DeepSeek 也不认，用 agent 配的那个 provider 才认的模型名
10. **LLM client 要在 executor 初始化完客户端后再注入**——`AgentMemory` 构造时 executor 的 `openai_client` 还是 None（`_initialize_clients` 在后面才调），所以注入要放在 client 就绪之后
11. **ChromaDB 是可选依赖**——没装 chromadb 时自动回退 HNSW，log 个警告，不让整个系统起不来

## 和 Agent 的关系

每个 Agent 有自己独立的记忆系统（独立的向量库 collection、记忆图、缓存），互不干扰。Agent 配置里可以单独：

- 开关 RAG 记忆系统（`rag_enabled`）
- 开关 LLM 实体/关系抽取（`entity_extraction_enabled`）——开启后用 agent 自己的 LLM 抽取，不开则走共现回退
- 选 embedding 模型、配压缩用的小模型

LLM 抽取的客户端**复用 agent 自己配置的 LLM**（executor 初始化完 `openai_client` 后注入到 RAG 系统），不单独配 key——所以 DeepSeek agent 用 DeepSeek 抽取，Kimi agent 用 Kimi 抽取，天然支持各 provider。Gemini agent 没有 OpenAI 兼容客户端，抽取自动跳过走共现，不报错。

ChromaDB 持久化目录全局一个（`data/chroma/`），每个 agent 在里面建自己的 collection（名字带 agent_id），互不干扰。前端的"记忆洞察"面板展示的就是这套系统的统计：多少文档、多少实体、多少关系、压缩比、缓存命中率。

***

## 现状与局限

这套系统现在是 **HNSW/ChromaDB 双后端 + LLM 抽取 + 持久化** 的混合架构：

- 向量索引可选纯内存 HNSW（零依赖）或 ChromaDB（持久化），默认按 agent 配置走
- 中文实体和语义关系由 LLM 抽取，不再依赖首字母大写启发式
- 向量和实体图都持久化到 ChromaDB，重启不丢
- 没 LLM 配置或调用失败时自动回退共现，保证基本可用

仍有的局限：

- **ChromaDB 依赖较重**（~100MB，带 onnxruntime/tokenizers），但设为可选，不装就回退 HNSW
- **LLM 抽取有成本**——每个 chunk 多一次 LLM 调用，受 `entity_extraction_enabled` 门控，默认关
- **实体抽取质量取决于 LLM**——小模型可能漏抽或乱编关系，prompt 里已要求"只抽明确体现的关系，不要臆测"
- **历史数据不会自动补抽取**——启动加载只把向量入 ChromaDB、从 metadata 重建图；老记忆（没有 relations metadata 的）图里就没关系，要重新 `add_dialogue` 才会抽
- **倒排索引和时间索引仍是内存**——启动时从 ChromaDB 全量回填，文档多了启动会慢
- **PQ 量化已实现但没接入**检索路径

未来可以做的：历史数据补抽取的 admin 端点、PQ 量化接入存储省内存、中文分词改进关键词索引、多 Agent 共享记忆池。
